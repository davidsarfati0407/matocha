# Décisions — backend (API Ops, back-office, liste d'attente, commerce)

| # | Décision | Raison | Alternative écartée |
|---|---|---|---|
| B1 | Stockage derrière une interface `Store` à forme de table, avec deux adaptateurs : Supabase (PostgREST en `fetch`, clé service-role côté serveur) et mémoire (tests/dev, refusé en production). | Pas de SDK lourd ; même code testé en mémoire et exécuté sur Supabase ; changement de base possible sans toucher aux routes. | `@supabase/supabase-js` : dépendance de plus pour quelques requêtes simples. |
| B2 | RLS activée sur toutes les tables **sans aucune politique** ; droits `anon` et `authenticated` révoqués. | Rien n'est lisible depuis le navigateur ; toute lecture passe par le serveur. | Politiques par rôle : inutiles sans accès client direct. |
| B3 | Magic link d'administration maison (HMAC + usage unique + session hachée), pas Supabase Auth. | Fonctionne avec n'importe quel adaptateur de stockage, la liste blanche `ADMIN_EMAILS` est vérifiée à chaque requête, et `/admin/dev-login` (désactivé en production) permet des captures Playwright sans e-mail. | Supabase Auth magic link : lie l'authentification au fournisseur de base et complique les tests. |
| B4 | E-mail via l'API HTTP de Resend (un seul `fetch`). Brevo peut être ajouté derrière la même interface `EmailSender`. | Le plus simple à brancher ; double opt-in et désinscription RFC 8058 (`List-Unsubscribe-Post`). | Brevo : équivalent, à choisir selon le prix et la délivrabilité. |
| B5 | La liste d'attente répond toujours `pending` (nouvelle adresse, en attente, déjà confirmée). | N'expose pas qui est inscrit. Pas de second e-mail avant 10 minutes. | Messages distincts : fuite d'information. |
| B6 | Sans stockage ni service e-mail, `POST /api/waitlist` renvoie 503 `not_configured` et `isWaitlistOpen()` vaut `false`. | Règle du brief : jamais de fausse confirmation. | — |
| B7 | IP jamais stockée : `sha256(ip + IP_HASH_SALT)`. | Minimisation RGPD tout en permettant de repérer des abus. | — |
| B8 | Une seule route attrape-tout `/api/ops/v1/[...path]` + un routeur déclaratif, et une couche de service partagée avec le serveur MCP. | Auth, scopes, idempotence, débit et audit sont identiques en REST et en MCP ; un seul endroit à tester. | Un fichier `route.ts` par endpoint : logique transverse dupliquée. |
| B9 | MCP minimal fait main (JSON-RPC sur POST, sans état, réponses JSON). | Pas de session ni de SSE à maintenir sur Vercel ; suffisant pour `tools/list` et `tools/call`. | `@modelcontextprotocol/sdk` : plus complet mais plus lourd pour neuf méthodes. |
| B10 | `PATCH /catalog/recipes/:id` ne peut écrire que des Proof `to_confirm` ; toute confirmation passe par `POST …/proofs` puis une validation humaine. | Un agent ne peut pas transformer une hypothèse en fait. | — |
| B11 | `POST /catalog/packs/:id/status` est appliqué directement sauf vers `available` (validation). | Conforme au tableau §11.4. | — |
| B12 | Publication de contenu : `POST /content/blocks` crée un brouillon, `POST /content/blocks/:id/publish` crée la demande. | Le tableau §11.4 regroupe `GET/POST /content/blocks` ; la publication a besoin d'une cible explicite. | — |
| B13 | Ajout de `GET /change-requests/:id` (non listé dans §11.4). | Permet à l'agent de suivre ses demandes sans webhook. Il ne voit que les siennes. | — |
| B14 | Le passage en vente exige deux verrous : `SITE_MODE_SALE_UNLOCK=true` sur le déploiement ET le réglage `site_mode = sale`, écrit uniquement par une demande approuvée dont la checklist est réévaluée **au moment de l'approbation**. | Une variable seule ne suffit pas, une approbation seule non plus. | — |
| B15 | Checklist : société confirmée (opérateur, forme, immatriculation, adresse), `legal_pages_complete`, au moins un pack qui passe `buyBlockers("sale", …)`, Stripe configuré, `shipping_configured`. Les deux drapeaux sont déclarés par un admin et journalisés. | Ces éléments ne sont pas vérifiables automatiquement. | — |
| B16 | Webhooks : première tentative immédiate, puis rejeu exponentiel par le cron `/api/cron/webhooks` (protégé par `CRON_SECRET`). | Une fonction serverless ne doit pas dormir plusieurs minutes. **À configurer** : un cron Vercel toutes les minutes ou toutes les 5 minutes. | `setTimeout` en mémoire : perdu au recyclage de l'instance. |
| B17 | Stripe Checkout hébergé via REST, clé d'idempotence dérivée de l'`Idempotency-Key` du clic : un double envoi renvoie la même session. Prix recalculés côté serveur depuis le catalogue. | Pas de SDK ; aucune confiance dans le prix envoyé par le client. | — |
| B18 | Le webhook Stripe répond 503 hors mode vente. | Stripe rejoue pendant 3 jours : rien n'est perdu si le mode est brièvement rebasculé. | Traiter quand même : contredirait le verrou. |
| B19 | Expédition : interface `ShippingProvider` seulement (Sendcloud ou Boxtal à choisir). Sans connecteur, `POST /orders/:id/shipments` exige transporteur et numéro de suivi (saisie manuelle). | Pas de transporteur contractualisé. | — |
| B20 | Statistiques : inscriptions, confirmations, commandes et chiffre d'affaires depuis la base ; visites via l'API Plausible si `PLAUSIBLE_*` est renseigné, sinon `null`. | Vercel Analytics n'expose pas d'API de lecture. | Inventer un chiffre de visites : exclu. |
| B21 | `stock.low` est déclaré mais jamais émis. | Il n'y a pas de stock à suivre avant le premier lot. | — |
| B22 | Export CSV : cellules commençant par `= + - @` préfixées d'une apostrophe. | Évite l'injection de formules dans un tableur. | — |
